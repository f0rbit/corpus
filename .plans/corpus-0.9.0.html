Plan: corpus 0.9.0 — entity scoping and silent-wrong-result fixes

todo

Closes the remaining items of #57. It adds a first-class entity_key to snapshots and observations, so a shared store can hold many entities. Querying by entity and is_stale then work per entity, without dynamic store ids. The release also fixes a family of APIs that return wrong results without any error: version_filter combined with limit returns too few rows, unknown query keys are ignored, DataStorage throws escape, and listing errors end iterators without an error. It replaces the throwing build() with a typed builder, removes the include_stale documentation for a feature that was never built, and adds devpad's two manifest fields. This is a minor release with one consumer migration (two nullable columns). Research: /tmp/corpus-0.9.0-scoping.md. Approved 2026-11-07, all recommendations accepted.

Root cause

Stated goal: ship the #57 items deferred from 0.8.2 (entity-scoped query and staleness, typed builder, per-field provenance), the version_filter/limit bug and the create_data_client throw mapping.

Underlying need: a crawl → extract → diff pipeline needs one store per source type holding many entities. Corpus's unit of "current" today is the whole store, which forces either one store per entity (losing static store typing) or hand-rolled filtering in JS. Separately, several query paths return incomplete or unfiltered results without saying so. That is worse than an error for a library that promises Results everywhere.

Why this matters: an observation-only entity_key (what #57 literally asks for) can't answer "is my extraction for entity A out of date?". Only the snapshots know which entity a new crawl is about. Scoping entities on observations alone would leave is_stale as wrong as it is today.

Alternatives considered

The architectural choice is how to model the entity. The other items are bounded fixes with one clear design each, covered in the phases.

Option 1: First-class entity_key on snapshots and observations

recommended

Add a nullable entity_key column (indexed with store_id) to corpus_snapshots, and a nullable entity_key column (indexed with type) to corpus_observations. API changes:

  • store.put(data, { entity_key }), store.get_latest({ entity_key }) and store.list({ entity_key }).
  • observations.put({ entity_key? }). When omitted, the key is inherited from the source snapshot.
  • query({ entity_key }).
  • is_stale(pointer) becomes entity-aware without a signature change. If the source snapshot has an entity_key, the pointer is stale when a newer snapshot with the same key exists in that store. Otherwise the current store-wide rule applies.

Real-world examples

  • Kafka log compaction: one topic holds many keys, and "latest" is per message key, not per topic. source
  • S3 object versioning: one bucket, version history and "current" per object key. source
  • dbt snapshots: rows are versioned per unique_key in one table, and validity is scoped per key. source

Pros

  • is_stale becomes correct for the issue's case, and existing data with no entity_key keeps today's behaviour exactly.
  • 0.8.2's insertion-order tie-break and newest-first list make "latest per entity" a single indexed LIMIT 1 query on every backend.
  • One drizzle-kit generate covers both columns, so consumers pay one migration.
  • Inheriting the key at observations.put means the entity is defined once, on the snapshot.

Cons

  • Changes SnapshotMeta, which ripples to raw_snapshot_meta_schema (utils.ts), the file backend's _meta.json, CLI serialize_meta (an additive --json field), copy() (verbatim) and the fake D1 DDL.
  • A 0.9.0 Worker against an un-migrated D1 fails, because drizzle selects columns explicitly. This needs to be loud in the release notes.
  • Inheritance costs one metadata.get per observations.put when the key is omitted.
  • Custom MetadataClient implementations that ignore the new option still compile but return store-wide results.

Architecture decisions

  • Entity staleness is source-driven and automatic for keyed data (D2). is_stale(pointer) keeps its signature: it reads the source snapshot's meta, and if that meta has an entity_key it compares against get_latest(store, { entity_key }). Unkeyed snapshots behave exactly as in 0.8.x. Corpus.is_superseded follows automatically.
  • Explicit observation entity_key may differ from the source's (D1): it overrides inheritance, so one page can yield per-entity observations. is_stale still keys off the source snapshot's entity; the JSDoc says so.
  • if_changed with an entity_key compares against that entity's latest.
  • include_stale: delete the claims. It never existed; building it would change default query semantics. The guide gets a "current observations only" recipe instead.
  • version_filter with limit. Set/array → StorageQueryOpts.source_version_in (SQL inArray, shared JS filter), before LIMIT. Function filter → the client drops the storage limit and applies it after filtering; the JSDoc notes the scan cost.
  • Unknown query keys (D3): exact-keys generic at compile time; at runtime a strict zod/v4 key check emits a validation_error event through the backend's on_event and yields nothing (matches list()). No new throw site.
  • Typed builder. create_corpus() returns a builder without build; with_backend returns CorpusBuilderWithBackend<Stores>. Each step returns a new builder over copied state (today definitions.push at corpus.ts:364 shares one closure, so branches leak). The runtime throw stays for untyped callers.
  • Listing errors. collect_listing(tracker, iterable) → Result<T[]>, built on on_event; the CLI switches to it.
  • Per-field provenance (#57 item 10): won't-do. The content-schema pattern from the 0.8.2 docs already covers it.
  • File-backend layout fix stays deferred (D4).
  • Devpad manifest fields (D5): add both as optional, additive fields.
