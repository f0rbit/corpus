Plan: test-suite-yield

approved

Make the corpus test suite smaller and stronger at the same time. Today 1164 tests / 14.5k LOC reach 87.2% lines / 91.5% functions, but 684 of the 885 tests in the heaviest files add no line coverage and are mostly literal-variation examples. Two observation suites are copy-pasted, and real code (drizzle delete_by_source, layered observations, remote tx compensation, wrap_bytes_storage, merge_deep/at) has no coverage at all. The plan does four things. It adds two cheap, mechanical safety rails: a coverage-superset diff and a mutation kill-set check. It turns example clusters into testing.* laws and properties. It replaces copy-paste with shared contract suites and model-based equivalence across all five backends. It fills the ranked coverage gaps and then turns on the deferred per-file 80% CI coverage gate (devpad task_c453a4e2). Expected result: about 1164 → about 750 tests, about 14.5k → about 9.5k test LOC, lines 87.2% → ≥93%, functions 91.5% → ≥96%, and no lib file under 80%.

Root cause

Stated goal: Remove low-value and low-yield unit tests, widen the high-value tests, and lean on properties, fuzzing and generators instead of repeated examples. The test for "low-yield" is: does removing it lower coverage?

Underlying need: A suite where each test earns its keep, i.e. its removal would let a real bug through. Each behaviour should be specified once (a law, a contract or a model) and checked across every implementation, not re-typed per backend or per literal. Line coverage is the cheap proxy for this, but it can't distinguish inputs and bun reports no branches. So "does removing it lower coverage?" has to be extended to "does removing it lower coverage or let a mutation survive?".

Why this matters: Pure coverage-driven deletion is known to lose fault-detection power (Rothermel et al. found large losses for coverage-preserving reductions). Done naively, it would delete the mutation-proven regression guards (tie-break, SQL-before-LIMIT, parseArgs tokens, selector key, --json purity), because those deliberately add zero lines. Separately, the duplication is why the uncovered code exists. Nobody wrote observation tests for layered, cloudflare or remote because each backend needed its own copy-pasted file.

Alternatives considered

Option 1: Specify once, check everywhere, delete under a mutation gate

recommended

Combines the audit's three levers behind two mechanical rails. (1) Pure-function example clusters become testing.* laws and properties (Result, observation utils, codecs, parallel_map, CLI policy, substrate self-tests, version-set). (2) Duplicated integration suites become shared contract suites: a new run_observations_contract_tests over 5 backends plus an observations provider_equivalence model. (3) backend-equivalence gains filtered-list, get_latest, children, hash and store-list commands and the cloudflare and remote providers. The contract assertions it now subsumes are then pruned, except the named regression guards. Every deletion has to pass a per-file coverage-superset diff against the base ref and a hand-curated mutation kill-set check (new kill set ⊇ old kill set). The plan finishes with gap-filling and the per-file 80% coverage gate in CI.

Real-world examples

  • CockroachDB Pebble: a metamorphic test runs generated op sequences against several configurations and diffs their outputs, instead of hand-written per-config cases. This is the shape of backend-equivalence extended to 5 backends. source
  • Go testing/fstest.TestFS and x/net/nettest.TestConn: one conformance suite that every fs.FS / net.Conn implementation runs, replacing per-implementation copies. This is the shape of the observations contract suite. source
  • Google diff-based mutation testing: a small number of mutants, chosen per change and surfaced in code review, instead of whole-codebase mutation runs. This is the model for the per-cluster manifest check. source

Pros

  • Line coverage goes up while test count goes down. The observations contract alone covers drizzle delete_by_source (370-393), the filter branches (323-335) and layered observations (246-300), which are uncovered today.
  • Deletions are defensible. Each cluster commit carries proof: a coverage superset and a kill-set superset. Bun has no branch coverage, and the mutation check is the substitute.
  • Reuses machinery corpus already ships (law.round_trip, law.functor, provider_equivalence, equivalence_command, testing.arb), which dogfoods the substrate downstream packages are told to use.
  • Ends with the coverage gate the repo already declares but doesn't enforce (bunfig.toml coverageThreshold = 0.8, devpad task_c453a4e2).

Cons

  • Biggest lift: 4 phases and about 16 cluster commits. The mutation manifests are hand-authored, and their quality depends on the coder's choice of mutants (mitigation: minimum one mutant per deleted describe block, plus a durable regression-guard manifest).
  • Adding cloudflare and remote to the equivalence law costs runtime (fake D1 DDL per run; Bun.serve for remote). Resolved in Q1: one shared transport per file with fresh fake state per run, measured first.
  • Making cli-entrypoint coverage visible needs a small, behaviour-preserving lib change (cli/main.ts).

Option 2: Delete-only by greedy set cover

Real-world examples

Option 4: Mutation-score-driven pruning with StrykerJS

Real-world examples

Pros

Architecture decisions

AD-1: Deletion criterion (all four must hold, per cluster)

  1. Coverage superset. bun run coverage:diff against the merge-base (6171c87) shows, for every lib file, that the covered line set is a superset of the base set and the function hit count is ≥ base. Lib source is frozen for Phases 1-3, so line identity is exact. Phase 4's one lib change (cli/main.ts) is re-baselined at its own commit.
  2. Not on the KEEP list. These stay regardless of yield:
    • Type-level tests: transaction-types, observation-query-types, cloudflare-binding-types, builder-types, schema-entry.
    • Documented-bug guards: list eq() exact-match; tag-before-limit; entity-before-limit; version_filter-before-limit; get_latest insertion tie-break; parseArgs token reconstruction; selector key presence; lineage (cycle); --json purity; data-key aliasing guard; "bad token ≠ empty db" (listing-errors, cli-entrypoint); dev-checkout walker guard; put-if-changed revert/tombstone; file concurrency and transaction recovery.
    • Fake-fidelity tests: http-fakes.
    • Reference laws cited by AGENTS.md: corpus-error-paths, copy-laws, vending-pilot, backend-roundtrip, backend-equivalence, result-functor.
    A guard may move (e.g. into a contract suite) but keeps its exact assertion and its AGENTS.md citation is updated.
  3. Mutation kill-set superset. bun run mutate tests/mutations/<cluster>.ts reports Knew ⊇ Kold. Survivors in both runs are logged as known gaps, not blockers.
  4. Replacement first. The replacement property or contract lands in the same diff as the deletion, never later (refactor rule: delete last).

AD-2: Mutation-check procedure (cheap, bun-native, no framework)

A manifest is a typed .ts file (not *.test.ts, so bun test ignores it):

export type Mutation = {
  readonly id: string;          // "result/unwrap_or-swaps-branches"
  readonly file: string;        // lib path, repo-relative
  readonly find: string;        // must match EXACTLY once, or the manifest is stale → fail
  readonly replace: string;
  readonly guards: string;      // the behaviour / deleted describe block it stands for
};
export type MutationManifest = {
  readonly cluster: string;
  readonly old_tests: readonly string[];   // test files at the base ref that covered this cluster
  readonly new_tests: readonly string[];   // test files in the working tree after the change
  readonly mutations: readonly Mutation[];
};

scripts/mutation-check.ts <manifest> [--base HEAD] works as follows:

  1. It requires the change to be staged and snapshots it with git stash create, which captures staged new files without touching the checkout.
  2. It adds two detached worktrees under os.tmpdir() (base ref and snapshot) and symlinks node_modules into both. If bun.lock differs between them, it fails.
  3. It runs each side unmutated as a sanity check, so a red baseline can't fake kills.
  4. For each mutation and each side, it writes the mutant, runs bun test <side's files> (60 s timeout), records killed = non-zero exit, and restores the file.
  5. It prints Kold, Knew, regressions (Kold \ Knew) and survivors, exits 1 on any regression, and removes its own worktrees.

The main checkout is never mutated. Mutant selection rules for coders:

  • At least 1 mutant per deleted describe block, with at least 5 per cluster.
  • Prefer semantic mutants: boundary flips (<↔<=), negated guard, swapped ok/err branch, dropped filter/where term, reversed comparator, slice off-by-one, removed await.
  • Each mutant must still typecheck. Bun strips types, so a non-compiling mutant would be a false "kill" signal that a reader can't trust.

tests/mutations/guards.ts re-introduces every KEEP-list bug once (e.g. eq(→like( in the drizzle list, args:→argv: in cli/args.ts, removed tie-break rowid ordering) with old_tests = new_tests = the current suite, so you can re-prove that the guards still bite at any time.

AD-3: Coverage floor is two-tier

  • During the refactor (per cluster): the exact line-set superset from AD-1, which is stricter than any percentage.
  • Permanently: the existing bunfig.toml coverageThreshold = 0.8 (org standard, single source of truth), which bun enforces per file on lines and functions. It gets wired into CI and gate as bun test --coverage. This is exactly devpad task_c453a4e2, so Phase 4 adopts that task instead of minting a new one. No per-file baseline numbers are committed, because they would be a second source of truth that rots as lib code changes. There is no permanent ratchet (Q2): after this PR, the 80% floor is the only standing gate.
  • Baseline: 18 lib files are under 80% on lines or functions today. They are base, layered, remote-r2 (funcs), cat, lineage, show, stores, versions, config-schema, load-config (funcs), lookup, output, wrangler (funcs), encrypt, corpus, sst, laws/equality and laws/functor. sst.ts (a 9-line IaC naming helper) is excluded via coveragePathIgnorePatterns with a why-comment and gets no test (Q2).   • What moves to the model: plain CRUD and listing semantics become model-checked across all backends. New commands:

AD-5: Observations get the same two-layer shape

  • run_observations_contract_tests(name, factory, cleanup?) covers type validation, optional fields, timestamps, id format, events, unknown-key rejection and is_stale. It runs over memory, file, layered, cloudflare and remote.
  • An observations provider_equivalence model covers put/get/delete/delete_by_source and query/query_meta filters: type, source_store/version/prefix, version_filter (Set ≡ array ≡ predicate), exclude_version, entity_key, created/observed ranges and limit. The model uses the AGENTS.md ordering rule: created_at desc, later insertion first.
  • File-persistence-across-instances tests stay file-specific.

AD-6: Property-test discipline

  • Everything goes through the testing.* substrate or the in-repo testing/ imports, which is the existing tests convention. Tests import root zod so the test:zod3 matrix exercises both generations.
  • Any fc.assert over a compose arbitrary that can fail gets { endOnFailure: true }.
  • Dates are clamped to 2000-2100. Use stringMatching instead of hexaString, a tight email arb for .email(), and noDefaultInfinity for zod-4 numbers.
  • The CLI enable matrix is exhaustive over all 32 combinations (a loop over fc.sample-free enumeration), not sampled.
  • New property files go under tests/property/. Run counts follow the module defaults unless a test documents why not.

Not applicable: no pages or nav (test-only refactor plus one CLI-internal extraction).

Phases

Executed by the build stage: background coders write diffs and may self-check with bun run typecheck, bun run lint and bun run fmt only, with no tests, builds, installs or git. That matters here, because coders cannot run bun test, coverage:diff or mutate. They author the mutation manifests and the reviewer executes them. Disjoint-file tasks share the checkout; overlapping work uses per-coder worktrees, integrated linearly by the reviewer. Sequential execution is for true ordering dependencies. The reviewer runs the full gate per unit, fixes failures, and commits. Per cluster, the reviewer also runs bun run coverage:diff and bun run mutate tests/mutations/<cluster>.ts (AD-1/AD-2) before committing. That means one commit per cluster (C0-C16) on branch test/suite-yield and ONE PR at the end. Verification, the adversary checklist and proof are captured once per phase.
